# 2026-08-31 Milestone

## 微信入站审批与会议纪要上下文优化（v2.0.8）

### 背景

2.0.7 发布后继续围绕两个方向收尾：

- 微信通知不应只做单向推送，还需要支持用户在微信里直接查询待办、审批任务、批量审批，并在推送通道临近失效前提醒用户保活。
- 会议纪要生成时，模型只拿到转写正文，未显式拿到 `meeting_date`，导致纪要中经常输出“时间未注明”。
- 删除带转写分段的会议记录时，生产环境触发 MySQL 外键约束，返回 500。
- 开发和生产的会议纪要生成模型需要改为 Moonshot Kimi K3，但真实 API key 只允许写入两端 `.env`，不能进入 Git。

### 后端实现

#### 会议记录

- `backend/app/api/meeting.py`
  - `DELETE /meeting/records/{id}` 改为先通过数据库批量删除 `MeetingTranscriptSegment`，并 `flush()` 后再删除 `MeetingRecord`，修复生产外键顺序导致的 500。
  - 新增 `_build_meeting_summary_user_message()`，会议纪要生成时统一构造“会议基础信息”上下文。
  - `POST /meeting/records/{id}/summarize` 会把会议标题、会议日期、参会人员、上次会议纪要和当前转写文稿一起传给 LLM。
  - system prompt 明确要求：如果会议基础信息包含会议日期，则以该日期作为会议时间/日期依据，不输出“时间未注明”。

- `backend/tests/test_meeting_transcript_import.py`
  - 增加删除带转写分段会议的外键顺序测试。
  - 增加会议纪要上下文包含会议日期的测试。
  - SQLite 测试启用外键约束，并创建测试用户满足 `created_by` 外键。

#### 微信通知与入站消息

- `backend/app/services/wechat_inbound.py`
  - 新增微信入站消息处理：引用/单号/编号审批、“待办”指令、批量审批和 LiteLLM 兜底对话。
  - “待办/审批/审核”等短指令会查询真实待审批任务并逐条推送，每条带编号和单号；个人进行中待办只返回数量。
  - 支持“通过 1”“拒绝 2 理由:xxx”“通过 <todo_id>”等审批指令。
  - 支持“全部通过”“都同意”“通过全部”“全部拒绝 理由:xxx”等批量审批指令。
  - 审批关联请假单时，同步审批/驳回对应 `LeaveRequest`，避免待办完成但请假单仍停在 pending。
  - LLM 兜底对话注入实时待办/审批数量，无法确认具体事项时引导用户发送“待办”，避免编造。

- `backend/app/api/wechat_notify.py`
  - 新增 `POST /wechat-notify/inbound`，供 weixin-msg-service 转发用户微信消息。
  - 入站接口按 `account_id` 找到绑定用户，记录 `last_inbound_at`，并调用入站消息处理服务。
  - 新增 `POST /wechat-notify/flush`，用于用户通道重新激活后立即补发离线通知。

- `backend/app/services/wechat_notify_queue.py`
  - 离线通知队列保留 FIFO 补发机制。
  - 新增通道保活检查：用户最近一次微信来信后约 24 小时内 context token 有效；距过期不足 1 小时时，给用户推送一次保活提醒。
  - `wechat_notification_retry_worker()` 每轮同时执行队列补发和保活提醒检查。

- `backend/app/models/shared.py`
  - `WeChatNotifyBinding` 新增 `last_inbound_at`、`keepalive_notified_at`。

- `backend/db_migrations/versions/20260818_0001_binding_inbound_tracking.py`
  - 为 `wechat_notify_binding` 增加 `last_inbound_at` 和 `keepalive_notified_at` 两列。

### AI 模型配置

- 开发环境 `backend/.env` 和生产环境 `/srv/punkrecord/backend/.env` 已配置：
  - `LITELLM_BASE_URL=https://api.moonshot.cn/v1`
  - `LITELLM_MODEL=kimi-k3`
  - `LITELLM_API_KEY` 为环境私密值，不写入 Git。
- `backend/.env.example` 只保留占位 key：`your_kimi_api_key`。
- `backend/app/core/config.py` 的默认 LLM 地址/模型同步为 `https://api.moonshot.cn/v1` / `kimi-k3`，默认 key 为空，避免仓库文件继续携带真实密钥。
- `backend/app/api/ai.py` 只对旧 `gemini-*` 短模型名自动补 `gemini/` 前缀，`kimi-*` 等其他 OpenAI 兼容模型名保持原样，避免 Kimi 环境下 AI 对话/合同起草请求模型名错误。
- `.agent/workflows/project-overview.md` 记录当前 dev/prod 的会议纪要模型为 Kimi K3。
